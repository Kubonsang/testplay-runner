## 관찰 (발견 즉시 append)

### O1 — summary.json 계약의 기계 소비(신규 소비자 유형) 성립 `severity: confirm`

- **재현:** `testplay run --shadow --filter FIX_LINQ_PAT_01_Tests` 직후, PostToolUse 훅이 `find .testplay/runs -name summary.json -mmin -2 -exec ls -t {} + | head -1` → `jq .exit_code` → 디렉토리명을 run_id로 기록
- **관찰:** exit 0, summary.json = `{"exit_code":0,"failed":0,"passed":6,"run_id":"20260708-010723-bb0209f4","schema_version":"1","skipped":0,"total":6}` — run_id 필드와 디렉토리명 일치, exit_code는 정수형
- **기대:** run 완료 시 `.testplay/runs/<run_id>/summary.json`에 exit_code 존재 (README 산출물 계약)
- **실제:** 기대대로. 훅이 파싱한 값이 프로세스 exit code와 일치. 하네스의 done 게이트가 이 레코드로 통과함
- **우회:** 없음
- **비고:** 소비자가 사람/모델이 아니라 **셸 훅**인 첫 사례 — summary.json 스키마가 사실상 외부 API가 됨. 스키마 변경 시 이 소비자가 깨질 수 있다는 신호로 기록

### O2 — `testplay check` ready:true는 에디터 상태와 독립 `severity: confirm`

- **재현:** unity-cli 하트비트 117h+ 사망(wedged 에디터) 상태에서 `testplay check`
- **관찰:** exit 0, `"ready": true`
- **기대:** shadow가 자체 Unity 인스턴스를 띄우므로 에디터 무관 — 설계 의도로 이해
- **실제:** 기대대로. 단, "check ready = 파이프라인 전체 준비"로 오독하면 라이브 에디터가 필요한 후속 단계(unity-cli refresh --compile)에서야 실패가 드러남
- **우회:** 하네스 env-check가 testplay check + unity-cli status를 **둘 다** 보도록 설계돼 있어 실제 문제는 없었음
- **비고:** 결함 아님. check의 보장 범위를 문서에 한 줄 명시하면 오독 여지 제거

### O3 — summary.json에 backend 필드 부재 `severity: low` `silent: no`

- **재현:** 위 run의 summary.json 전체 필드 = exit_code/failed/passed/run_id/schema_version/skipped/total
- **기대:** 이 스킬 템플릿이 "출력의 `backend` 필드"를 요구 — 최근 버전 계약에 backend가 있다고 시사
- **실제:** v0.9.2 schema_version 1에는 없음
- **우회:** 명령행 플래그(--shadow)로 모드를 역추적
- **비고:** 추정: backend 필드는 v0.9.2 이후 릴리즈의 계약 — 버전 델타이거나 stdout에만 있는 필드. 자동화 소비자(O1)가 tree/backend 판별을 명령행 파싱에 의존 중이라, summary에 backend가 실리면 소비자 로직을 단순화할 수 있음
