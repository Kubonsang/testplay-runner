## Signing gate

The selected route is a DigiCert public-trust code-signing identity backed by
KeyLocker/Software Trust cloud HSM. Before any stable tag is created, an
independent throwaway executable must prove:

- South Korean individual issuance was accepted;
- `Get-AuthenticodeSignature` reports `Valid`;
- `signtool verify /pa /all /v` passes;
- Code Signing EKU and the expected publisher, issuer, certificate thumbprint,
  and RFC 3161 timestamp are present;
- the signing private key is not exported into the repository or a general
  GitHub secret.

The proof ZIP and SHA-256, publisher identity, issuer, serial, thumbprint, and
timestamp evidence will be added here after acquisition. Until then,
`v0.13.0` must not be tagged.

## Candidate and exact-asset gates

The protected `stable-signing` environment holds only the DigiCert client
authentication material and signing identifiers. A manually dispatched
candidate run executes the same build, signing, signature verification,
packaging, checksum, and attestation sequence as the tag workflow but does not
create a release.

After candidate PASS, a separately approved annotated `v0.13.0` tag may create
a draft non-prerelease. The exact draft Windows archives must then pass:

- archive/checksum/attestation verification;
- Authenticode publisher and timestamp verification for both Windows EXEs;
- CLI version/help/config and helper hello contracts;
- fresh install, same-version upgrade, limited-user broker probe, fixture
  EditMode 2/2 and PlayMode 1/1, semantic parity, release, and uninstall;
- zero service, store, VHDX, mount, disk, drive-letter, and process residual.

Only a passing exact draft may be published and marked latest. The final
verdict is limited to:

```text
VHDX_DIFF_EXPERIMENTAL_OPT_IN_V0_13_0_RELEASED
```

Automatic `auto` promotion, GNF_ 8 workers, long-running child growth,
multi-hardware compatibility, generalized performance superiority, and
production readiness remain `NOT MEASURED`.
