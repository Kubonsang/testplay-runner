§1 · The complaint

Automation-hostile by default

Unity's raw CLI was built for humans clicking a window. Point an AI agent or a CI pipeline at it, and every failure mode looks the same. testplay exists to make each outcome legible — the lie on the left, the record on the right.

§2 · Execution paths

Three ways to run.
One identical contract.

The Unity Editor holds your project hostage with a single lockfile. testplay negotiates: a three-tier backend picks the fastest path that is still honest — and like a carbon-copy form, all three produce the same result, the same JSON, the same exit codes.

Originalbackend: "bridge"

Runs warm

A tiny opt-in C# package runs EditMode tests inside your already-open Editor via TestRunnerApi. No copy, no cold domain reload. A "Pristine Gate" refuses the warm path whenever it could change results.

Duplicatebackend: "shadow"

Runs isolated

Editor open but bridge unavailable? Tests run cold in a per-run .testplay-shadow-<run_id>/ workspace with a warm Library cache. All paths in the output are remapped back to your real project.

Triplicatebackend: "process"

Runs cold

No editor in the way? Plain cold batchmode against the real project. The boring, hermetic default.

Honesty rule: the warm path is forbidden whenever warm-vs-cold could change results. Play Mode active? Compile pending? Foreign test run in flight? The bridge self-demotes to the cold path — and the backend field in the JSON tells you exactly which copy produced your results. You never have to infer provenance.

§3 · The agent interface

Six commands. That's the entire surface.

An AI agent's whole interaction model fits in one prompt paragraph. Every command emits one versioned JSON object and nothing else.

§3.0init

Generate testplay.json with sane defaults.

§3.1check

Validate Unity path, project, config — before touching Unity.

§3.2list

Candidate test names for --filter, with an honest complete flag.

§3.3run

Execute. Poll testplay-status.json for live phase.

§3.4result

Re-read history, pick a baseline for --compare-run.

§3.5version

JSON, like everything else.

Why agents like it

  • Deterministic branching — one exit code per failure class; recovery action is mechanical.
  • File + line, always — every path field ships both relative file and absolute_path. No path guessing across platforms.
  • Failure excerpts — excerpt: "message (at File.cs:42)" puts triage in the first read.
  • Regression truth — new_failures is only ever populated when a comparison actually happened. Empty means compared-and-clean, absent means not-compared.
  • Multi-instance scenarios — host/client orchestration with dependency gating, per-instance env injection, and an NDJSON IPC bus for network tests.
The agent loop
# 1. validate environment
testplay check

# 2. run with regression baseline
testplay run --compare-run 20260707-091500-b2c4d6e8

# 3. branch on exit code
#    2 → fix errors[].absolute_path:line
#    3 → fix tests[].absolute_path:line
#    4 → check timeout_type

# 4. meanwhile, poll progress
cat testplay-status.json
{ "phase": "compiling", "seq": 7, ... }

§4 · Quick start

Running in three commands

Pre-built binaries for macOS, Linux (amd64/arm64) and Windows — or build from source with a single go build.

Install — from source
git clone https://github.com/Kubonsang/testplay-runner.git
cd testplay-runner
go build -o testplay ./cmd/testplay

Or grab a pre-built binary from GitHub Releases.

Configure & run
testplay init --unity-path /path/to/Unity
testplay check   # ready: true?
testplay run     # one JSON object. one honest exit code.
