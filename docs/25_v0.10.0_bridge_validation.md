# TestPlay Runner v0.10.0 — Warm-Editor Bridge Validation (Tier B)

**Date:** 2026-06-23
**Version under test:** `v0.10.0` (branch `feat/v0.10.0-warm-editor-bridge`, PR #30)
**Validated against:** real Unity **6000.3.8f1** (Unity 6) on macOS (darwin)

---

## Summary

The v0.10.0 warm-editor bridge was validated end-to-end against a live Unity 6
Editor. The C# package compiles, the file-based handshake/protocol works, and the
warm path (`backend: "bridge"`) produces results **byte-identical** to the cold
path (`process` / `shadow`) — including the hardest cases: a parameterized test,
a failing test, a compile error, and script changes that force a domain reload.

This is the "Tier B" gate from [`RELEASE-PLAN.md`](../RELEASE-PLAN.md) and
[`docs/24_v0.10.0_release_notes.md`](24_v0.10.0_release_notes.md). All five spikes
plus the domain-reload/compile-settle state machine **pass**, and the LTS gate
(#32) was re-run on **Unity 2022.3.62f3 LTS** with identical cold/bridge parity
(see "LTS re-run" below). v0.10.0 is ready to tag.

One pre-existing **cold-path** limitation was surfaced and filed as **issue #31**.

## Method & evidence

### 0. C# compiles in Unity 6

Added `com.testplay.bridge` to an isolated project's manifest and ran a batchmode
compile (`Unity -batchmode -nographics -quit -projectPath … -logFile …`). Unity
exited `0`; `Library/ScriptAssemblies/TestPlay.Bridge.Editor.dll` was produced
(`Csc … TestPlay.Bridge.Editor.dll`), with `UnityEditor.TestRunner.dll` /
`UnityEngine.TestRunner.dll` referenced and **no `error CS`** anywhere. The renamed
fixtures `TestPlaySmoke.EditMode.dll` / `TestPlaySmoke.PlayMode.dll` also compiled.

### 1–2. Parity + ToXml fidelity (parameterized + failing)

Test set: `EditModeSmoke.AlwaysPasses` (pass), `MoreTests.IsEven(2)` / `IsEven(4)`
(parameterized, pass), `MoreTests.FailsOnPurpose` (fail).

```
warm (--bridge):  exit 3  backend=bridge  total=4 pass=3 fail=1
cold (--no-bridge): exit 3  backend=shadow  total=4 pass=3 fail=1
exit/counts match: True
test set match:    True
PER-TEST PARITY:   PASS (identical)   # result, parameterized_group, excerpt, file, line
```

`IsEven(2)`/`IsEven(4)` carried `parameterized_group = TestPlaySmoke.MoreTests.IsEven`;
`FailsOnPurpose` carried the NUnit failure message/excerpt — all parsed identically
from the bridge-written `results.xml` and the cold `-testResults` XML.

### 3. Compile-error handling

Introduced `CS0103` (undefined name) in an EditMode test:

```
warm (--bridge):  exit 2  errors=[{file: MoreTests.cs, line: 10,
                                    message: "CS0103: The name 'undefinedSymbolForParity'
                                              does not exist in the current context"}]
cold (--no-bridge): exit 2  errors=[]      # see issue #31
```

Exit codes match. The warm sidecar (`CompilationPipeline.CompilerMessage[]`)
produced the complete, correct error. The cold stderr scrape returned empty
`errors[]` on Unity 6 — a **pre-existing cold-path limitation**, filed as **issue
#31** (the warm path is strictly better here).

### 4 (adjacent). Domain reload + recovery

Each script change above forced the warm Editor to `AssetDatabase.Refresh()`,
recompile, and reload the domain mid-request. The bridge's `SessionState`-backed
state machine resumed across every reload. After the compile error was fixed, a
fresh warm run returned `exit 0 backend=bridge total=3 pass=3` — confirming the
Editor recovered from the broken-compile state and handles back-to-back warm runs.

### 5. Cancellation + editor recovery (spike #4)

A 25 s `[Test]` (`Thread.Sleep`) was run via `--bridge`; `testplay` received SIGINT
~8 s in (mid-run):

```
testplay exit=8  backend=bridge  (no timeout_type)
.cancel marker:  requests/20260623-112531-f77edaec.cancel  written
testplay-status.json phase: interrupted
```

Identical to batchmode. The Editor then finished the abandoned run in the
background (its response, keyed to the abandoned run id, is ignored by the Go
client), returned to `idle` after ~30 s, and a fresh `--bridge` run — recompiling a
*changed* test (domain reload) — returned `exit 0 backend=bridge` (2/2). **The
Editor is recoverable after an interrupted run.** This validates the
abandon-and-timeout cancellation design (bridge-side *hard* cancellation remains
deferred, as planned).

### 6. Windows atomic file handoff (spike #5)

`internal/bridge/atomic_test.go` adds two 1000-iteration tests that hammer the
atomic request/response files with a concurrent writer and a tight reader,
asserting **no torn reads** and no rename failure under contention. They run on
every platform — including the CI `Test (windows-latest)` job — exercising
`os.Rename`'s `MoveFileExW(REPLACE_EXISTING)` semantics, which is exactly the
Windows sharing-violation / partial-read risk the spike targets.

**This spike found a real bug.** The first CI run **failed** on `windows-latest`:

```
rename …resp.json.tmp …resp.json: Access is denied.
```

On Windows, `os.Rename` / `File.Replace` fails with a sharing violation while a
concurrent reader has the destination briefly open — and the bridge's production
`writeAtomicJSON` (Go) *and* `AtomicFile.WriteAllText` (C#) both had this latent
defect, which would have broken the request/response handoff on Windows. Fixed by
retrying the replace-rename with a bounded ~1 s backoff on both sides (the
reader's handle is short-lived, so the race resolves quickly; POSIX rename is
unaffected). The atomic test now passes on `windows-latest` (`ok internal/bridge
3.2s`), and all of `test.yml` (ubuntu/macos/windows) is green on PR #30.

## LTS re-run (2026-06-24, Unity 2022.3.62f3)

The Tier B parity was re-run on **Unity 2022.3.62f3 LTS** (issue #32):

- C# package compiles clean (`TestPlay.Bridge.Editor.dll` built; 0 `CS` errors) —
  no Unity-6-only APIs.
- Warm `--bridge` run of the parameterized + failing fixture: `exit 3`,
  `parameterized_group` set on `IsEven(2)/(4)`, failure message captured. The
  `ITestResultAdaptor.ToXml()` root is `<test-suite>` on 2022.3 too, so the
  `<test-run>` wrapper parses identically — **review #7 does not materialize on
  2022.3 LTS**.
- **Cold (`shadow`) vs warm (`bridge`) parity: PASS — identical** (exit/counts +
  per-test result/parameterized_group/excerpt/file/line).

(Environment note: the LTS editor was installed on an external exFAT volume, which
seeds macOS AppleDouble `._*` files throughout the install; Unity's package
manager / C# compiler choke on them. Deleting `._*` from the install fixed it —
unrelated to testplay.)

## Caveats (remaining before tagging)

- **Unity 2021.3 LTS** was not separately run; the C# uses stable
  `TestRunnerApi` / `CompilationPipeline` APIs and compiled clean on both Unity 6
  and 2022.3, so divergence is unlikely. Run it too if 2021.3 is a target.
- **Issue #31** — cold-path compile-error *detail* on Unity 6 — is a tracked
  follow-up, not a tagging blocker (exit codes are correct; the warm path is
  unaffected).

## Conclusion

The warm-editor bridge **works end-to-end on real Unity 6 and Unity 2022.3.62f3
LTS** with exact cold/bridge parity across the hardest cases, validated mid-test
cancellation + Editor recovery, and a CI-Windows-validated atomic file protocol.
**Tier B passes** — spikes 1–5 plus the domain-reload/recovery state machine —
and the **LTS gate (#32) is satisfied on 2022.3**. v0.10.0 is ready to tag
(optional: also re-run on 2021.3 LTS). Issue #31 is a non-blocking follow-up.
