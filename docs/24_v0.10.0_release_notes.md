# TestPlay Runner v0.10.0 — Release Notes

**Status:** implemented on `main`; final tagging pending the release-gate validation spikes (see below).
**Previous release:** v0.9.2

---

## Summary

v0.10.0 — "The Warm-Editor Bridge" — removes the two physical bottlenecks that
appear when the Unity Editor is open: the shadow-workspace byte copy (disk,
용량) and the cold domain reload (time, 시간). Instead of working *around* the
open Editor by copying the project and cold-starting batch mode, testplay can
now run *through* the warm Editor.

An opt-in C# Editor package (`unity/com.testplay.bridge`) runs EditMode tests in
the already-open Editor via `TestRunnerApi` and writes the same NUnit
`results.xml` a cold run would. It is a **transparent backend**: the JSON/exit-code
contract is unchanged, with a new `backend` field disclosing which engine ran.

This stays inside the identity anchor (testplay is the honest *contract* layer,
not a TDD speed tool): the Test Runner window is a human GUI that automated
callers cannot use, so the bridge gives agents/CI the warm path humans already
have — *only* as a transparent backend, and *only* when it can prove a result
equivalent to a cold run. Speed/disk savings are a side effect, never a promise.

---

## What's New

### 1. Three-tier automatic backend selection

`testplay run` now selects a backend in this order, falling back automatically:

```
1. bridge   — a live, compatible, idle bridge is present AND the Pristine Gate passes
2. shadow   — else the Editor holds the project lock (Temp/UnityLockfile)
3. process  — else a fresh batch-mode process against the real project
```

This is the honest generalization of the prior shadow-vs-process choice: the same
"Editor open" trigger now prefers the warm bridge when it can be trusted, and
self-demotes to the unchanged cold path otherwise. Correctness wins by default.

### 2. `backend` field — always present (Output Design Rule #13)

Every `run` result (single-mode top level and each scenario `instances[]` entry)
now includes `backend`: `"process"`, `"shadow"`, or `"bridge"`. It is emitted
unconditionally, like `schema_version` — first-order provenance an agent should
never have to infer.

```json
{
  "schema_version": "1",
  "run_id": "20260622-101500-a3f8b2c1",
  "exit_code": 0,
  "backend": "bridge",
  "total": 2, "passed": 2, "failed": 0, "skipped": 0,
  "tests": [],
  "new_failures": null
}
```

### 3. The TestPlay Bridge Unity package (`com.testplay.bridge`)

A greenfield, in-repo UPM Editor package (EditMode only). **Dormant by default** —
installing it changes nothing. It activates only when opted in, and never in
batch mode:

- `TESTPLAY_BRIDGE_ENABLE=1` environment variable, or
- an empty `<project>/.testplay/bridge/ENABLE` sentinel file.

When active it heartbeats a handshake, runs requested EditMode tests via
`TestRunnerApi`, and reports results over a file-based protocol under
`<project>/.testplay/bridge/` (`handshake.json`, `requests/`, `responses/`,
`runs/<id>/status.ndjson` + `compile-errors.json`). `results.xml` is written to
the usual `.testplay/runs/<id>/` so the existing parse pipeline is reused
unchanged.

### 4. The Pristine Gate (hermeticity)

A warm result is returned only when the warm domain is equivalent to a fresh cold
domain for the code under test. The bridge:

- **refuses** (→ cold fallback) in Play Mode or for PlayMode requests;
- **waits** for compilation/import to settle, then reports compile errors as the
  same `exit 2` + `errors[]` a cold run would (the sidecar maps 1:1 onto the
  existing `CompileError` shape, message normalized to `CSxxxx: …`);
- **discloses** non-result-changing states (e.g. unsaved scenes) via `warnings`,
  and never auto-saves your editor.

### 5. Backend-selection overrides

- `testplay run --bridge` — prefer the bridge (still gated by the Pristine Gate;
  on a soft probe failure it falls back to cold with a disclosed `warnings` entry).
- `testplay run --no-bridge` — force the cold path.
- `testplay.json` `"bridge": { "enabled": false }` — forbid the bridge entirely.

---

## Unchanged

- **Exit codes 0–9** are unchanged; the bridge adds no new code. (Exit 7, shadow
  permission, is structurally impossible on the warm path.)
- The **six-command interface** (`init`/`version`/`check`/`list`/`run`/`result`)
  is unchanged.
- `testplay-status.json` schema is unchanged — the bridge reuses
  `compiling → running → done` and the Go side keeps sole ownership of the
  monotonic `seq` counter.

---

## Scope & Deferrals

- **EditMode only** this release. PlayMode through the bridge is deferred.
- **Two-phase** configs (`compile_ms` + `test_ms`) and **scenario mode** always
  run cold — the warm Editor cannot honestly reproduce the strict compile/test
  phase split, and multi-instance warm orchestration is deferred.
- Deferred to later versions: PlayMode-warm, scenario/network warm orchestration
  (the actual NGO/Mirror goal), bridge-side mid-test hard cancellation.

---

## Upgrade Notes

- No action required for existing agents/CI — the contract is unchanged and the
  bridge is off until opted in. Cold runs behave exactly as before, now stamped
  `backend: "process"` or `"shadow"`.
- To adopt the warm path: add `unity/com.testplay.bridge` as a UPM dependency,
  open the Editor with `TESTPLAY_BRIDGE_ENABLE=1` (or create the `ENABLE`
  sentinel), and run `testplay run` as usual.
- Agents may branch on `backend` for provenance/auditing; treat `warnings`
  entries prefixed `bridge:` as disclosures, not failures.

## Release Gate (pending before tagging)

Per RELEASE-PLAN.md, the following must pass against a real Unity install before
v0.10.0 is tagged:

1. **Cold/bridge parity** — `e2e/bridge_parity_test.go` (`//go:build e2e`):
   identical `tests[]`, exit codes, and `errors[]` (modulo absolute paths).
2. **`ITestResultAdaptor.ToXml()` fidelity** — parameterized + failing fixture
   round-trips through `parser.Parse` identically to cold `-testResults`.
3. **Compile-error parity** — warm sidecar `errors[]` byte-identical to the cold
   stderr scrape (modulo path).
4. **TestRunnerApi cancellation** — interrupting a run leaves the Editor
   recoverable for the next run.
5. **Windows atomic file handoff** under AV/indexer contention.
