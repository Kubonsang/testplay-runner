# testplay v0.13.0 release notes

`v0.13.0` promotes the seven-day-observed `v0.13.0-rc.1` lineage without
changing the native-tested Differencing VHDX provider. `vhdx-diff` remains an
experimental, explicit opt-in on Windows 11 x64; direct-batch and
legacy-shadow selection remain the default.

## Differencing VHDX workspaces

- One immutable dynamic NTFS parent VHDX is committed per compatibility key.
  Each run receives a private writable differencing child mounted at the
  isolated workspace's `Library`.
- A one-time elevated `testplay storage install` registers the LocalSystem
  broker for one Windows user SID. Ordinary CLI and AI-agent requests then use
  its authenticated local named pipe without elevation.
- Explicit `vhdx-diff` never falls back. Explicit `auto` may select `legacy`
  only when broker connection or capacity admission fails before parent or
  child work starts. Neither backend is selected implicitly.
- The default allocated-byte quota is 32 GiB, host-free floor is 20 GiB, and
  each newly admitted child reserves 2 GiB.
- The provider does not format a physical partition or modify ReFS, Dev Drive,
  Defender, or registry settings.

## Validation lineage

Provider logic remains frozen at
`beabf36a299572607232806807ad9b9c2d4cb222`. Native fixture and GNF_ 1/2/4
worker, forced-termination, broker-restart, Windows-reboot, quota/LRU, and
retained-workspace gates passed. The public RC completed its Day 0/3/7
observation on one Windows 11 x64 NTFS host with no blocking issue. See
[`docs/32_v0.13.0-rc.1_validation.md`](32_v0.13.0-rc.1_validation.md) and
[`docs/33_v0.13.0_rc_observation.md`](33_v0.13.0_rc_observation.md) for the
immutable artifact hashes.

The stable Windows `testplay.exe` and `testplay-storage-helper.exe` must have a
valid public-trust Authenticode signature and RFC 3161 timestamp. The release
workflow creates checksums and GitHub provenance only after signing. Verify all
three before approving the elevated broker installation. A valid signature
does not guarantee immediate SmartScreen reputation.

## Explicit limitations

- GNF_ four-worker preparation measured 14.794–15.122 seconds per worker,
  above the separate 10-second objective.
- GNF_ 8 workers, long-running child growth, and multi-hardware compatibility
  are not measured.
- Generalized performance superiority, automatic default promotion, and
  production readiness are not claimed.
