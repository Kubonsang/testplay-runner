testplay · Unity 테스트 자동화를 위한 계약 계층 · Apache-2.0 · Go · macOS / Linux / Windows

Unity 테스트 러너는 CI에게 거짓말을 합니다.

testplay가 진실을 말하게 만듭니다 — 서면으로.

Unity 테스트 러너를 AI 에이전트와 CI 파이프라인을 위한 안정적인 계약으로 감싸는 얇은 Go CLI: 구분되는 exit code, stdout에 JSON 객체 하나, 실시간 진행 파일, 그리고 silent failure 없음. 모든 실행이 정직한 기록을 남깁니다.

§1 · 고발장

기본값부터 자동화에 적대적입니다

Unity의 raw CLI는 창을 클릭하는 사람을 위해 만들어졌습니다. AI 에이전트나 CI 파이프라인을 붙이는 순간, 모든 실패가 똑같은 얼굴을 하고 있죠. testplay는 각 결과를 읽을 수 있게 만들기 위해 존재합니다 — 왼쪽이 거짓말, 오른쪽이 기록입니다.

The lie (raw Unity CLI)
The record (testplay)

컴파일이 실패해도 exit code 0

빌드가 깨졌는데 파이프라인은 초록불이 켜집니다.

exit 2 + errors[].absolute_path + line

컴파일 실패와 테스트 실패가 절대 섞이지 않습니다. 에이전트는 깨진 파일로 곧장 이동합니다.

결과가 NUnit XML 속에 파묻힘

모든 사용자가 각자 깨지기 쉬운 XML 파서를 다시 만듭니다.

stdout에 JSON 객체 하나

schema_version으로 버전 관리. 배너도 진행 표시 스팸도 없음 — 사람용 로그는 stderr로.

끝날 때까지 침묵

컴파일 중일까? 실행 중일까? 멈췄을까? 프로세스가 죽어야 알 수 있습니다.

실시간 testplay-status.json

원자적으로 갱신되는 phase + 단조 증가 seq. 파일 하나만 폴링하면 됩니다.

에디터가 열려 있으면? 프로젝트 잠김.

UnityLockfile 하나 때문에 사람이 창을 닫아줄 때까지 자동화가 멈춥니다.

bridge → shadow → process

정직할 수 있을 땐 warm 에디터로, 아니면 격리된 shadow workspace, 그다음 cold 프로세스로 자동 폴백.

타임아웃? 어떤 타임아웃?

멈춘 import와 느린 테스트 스위트가 똑같아 보입니다.

timeout_type: compile | test | total

2단계 데드라인이 "Unity가 컴파일조차 못 했다"와 "테스트가 느리다"를 분리합니다.

회귀 신호 없음

이 실패, 원래 있던 걸까? 내가 방금 깨뜨린 걸까?

--compare-run → new_failures

이전 run ID와 diff. 빈 배열이면 "비교했고, 회귀 없음" — 보장된 시맨틱입니다.

별표 A · 모든 실행에 첨부됨

exit code 11개. 모호함 0.

모든 exit code는 정확히 하나의 실패 클래스와 하나의 복구 액션에 대응합니다. 에이전트는 $? 하나만 보고 분기해도 항상 다음 행동을 알 수 있습니다.

Schedule A — exit code 시맨틱모든 커맨드에 구속력 있음
0

전체 테스트 통과

다음으로 진행.

1

의존성 오류

Unity/프로젝트를 못 찾음 — hint 필드가 환경 복구 방법을 알려줍니다.

2

컴파일 실패

errors[].absolute_path:line의 소스를 수정.

3

테스트 실패

실패한 테스트의 경로 + 라인 + excerpt로 곧장 이동.

4

타임아웃

timeout_type으로 분기: compile, test, total.

5

설정/사용법 오류

잘못된 testplay.json, 알 수 없는 키나 플래그. 의도적으로 엄격합니다.

6

빌드 실패

라이선스/빌드 타깃 문제 — Unity의 로그 소음에서 직접 감지.

7

권한 오류

shadow workspace가 파일시스템 권한 벽에 막힘.

8

시그널 중단

SIGINT/SIGTERM. 코드 수정 없이 재시도하면 됩니다.

9

러너 시스템 오류

결과 저장 실패 — 인프라 실패는 공개되지, 절대 숨겨지지 않습니다.

10

매칭 없음

--filter에 걸린 테스트가 0개. 아무것도 실행되지 않았고 — 그렇다고 말해줍니다.

§2 · 실행 경로

실행하는 방법은 세 가지.
계약은 하나로 동일.

Unity 에디터는 lockfile 하나로 프로젝트를 인질로 잡습니다. testplay는 협상합니다: 3-tier 백엔드가 정직함을 유지하는 선에서 가장 빠른 경로를 고릅니다 — 그리고 카본지 사본처럼, 세 경로 모두 같은 결과, 같은 JSON, 같은 exit code를 만들어냅니다.

Originalbackend: "bridge"

Warm으로 실행

옵트인 방식의 작은 C# 패키지가 TestRunnerApi를 통해 이미 열려 있는 에디터 안에서 EditMode 테스트를 실행합니다. 복사도, cold 도메인 리로드도 없음. "Pristine Gate"가 결과가 달라질 수 있는 상황에서는 warm 경로를 거부합니다.

Duplicatebackend: "shadow"

격리해서 실행

에디터는 열려 있는데 브리지를 못 쓴다면? run별로 격리된 .testplay-shadow-<run_id>/ workspace에서 warm Library 캐시와 함께 cold로 실행합니다. 출력의 모든 경로는 실제 프로젝트 경로로 다시 매핑됩니다.

Triplicatebackend: "process"

Cold로 실행

막아서는 에디터가 없다면? 실제 프로젝트에 대한 평범한 cold batchmode. 지루하지만 밀폐된(hermetic) 기본값입니다.

정직함의 규칙: warm과 cold의 결과가 달라질 수 있는 상황이면 warm 경로는 금지됩니다. Play Mode 켜짐? 컴파일 대기 중? 다른 테스트 실행 중? 브리지는 스스로 cold 경로로 강등되고 — JSON의 backend 필드가 어느 사본이 결과를 만들었는지 정확히 알려줍니다. 출처를 추측할 일이 없습니다.

§3 · 에이전트 인터페이스

커맨드 6개. 그게 표면의 전부입니다.

AI 에이전트의 상호작용 모델 전체가 프롬프트 한 문단에 들어갑니다. 모든 커맨드는 버전 관리되는 JSON 객체 하나만 출력하고, 그 외에는 아무것도 없습니다.

§3.0init

합리적 기본값으로 testplay.json 생성.

§3.1check

Unity 경로·프로젝트·설정 검증 — Unity를 건드리기 전에.

§3.2list

--filter 후보 테스트 이름들, 정직한 complete 플래그와 함께.

§3.3run

실행. testplay-status.json 폴링으로 실시간 phase 추적.

§3.4result

히스토리를 다시 읽고 --compare-run 기준점 선택.

§3.5version

이것도 물론 JSON.

에이전트가 좋아하는 이유

  • 결정론적 분기 — 실패 클래스당 exit code 하나. 복구 액션이 기계적으로 정해집니다.
  • 파일 + 라인, 언제나 — 모든 경로 필드는 상대 file과 absolute_path를 함께 제공. 플랫폼 간 경로 추측이 없습니다.
  • 실패 excerpt — excerpt: "message (at File.cs:42)"로 첫 읽기에서 바로 분류.
  • 회귀의 진실 — new_failures는 비교가 실제로 일어났을 때만 채워집니다. 빈 배열 = 비교했고 깨끗함, 없음 = 비교 안 함.
  • 멀티 인스턴스 시나리오 — host/client 오케스트레이션, 의존성 게이팅, 인스턴스별 env 주입, 네트워크 테스트용 NDJSON IPC 버스.
에이전트 루프
# 1. 환경 검증
testplay check

# 2. 회귀 기준점과 함께 실행
testplay run --compare-run 20260707-091500-b2c4d6e8

# 3. exit code로 분기
#    2 → errors[].absolute_path:line 수정
#    3 → tests[].absolute_path:line 수정
#    4 → timeout_type 확인

# 4. 그동안 진행 상황 폴링
cat testplay-status.json
{ "phase": "compiling", "seq": 7, ... }

§4 · 빠른 시작

커맨드 세 개면 실행됩니다

macOS, Linux (amd64/arm64), Windows용 사전 빌드 바이너리 — 또는 go build 한 번으로 소스에서 빌드.

설치 — 소스에서
git clone https://github.com/Kubonsang/testplay-runner.git
cd testplay-runner
go build -o testplay ./cmd/testplay

또는 GitHub Releases에서 사전 빌드 바이너리를 받으세요.

설정 & 실행
testplay init --unity-path /path/to/Unity
testplay check   # ready: true?
testplay run     # JSON 객체 하나. 정직한 exit code 하나.

Terms of the honest contract

testplay는 속도 계층이 아니라 계약 계층입니다.
속도와 정확성이 충돌하면 — 언제나 정확성이 이깁니다.
stdout = JSON only배너 없음. 진행 표시 줄 없음. 사람용 로그는 stderr로 가며, 에이전트는 그것을 완전히 무시해도 됩니다.
silent failure 없음실행된 테스트가 0개? 공개합니다. 결과 저장 실패? exit 9. warm 경로가 위험? cold로 폴백하고, 공개합니다.
출처는 언제나 공개backend 필드는 무조건 존재합니다. 결과를 만든 엔진을 추측할 일이 없습니다.
100% 로컬텔레메트리 없음, 계정 없음, 네트워크 호출 없음. 당신의 프로젝트는 당신의 것입니다.
