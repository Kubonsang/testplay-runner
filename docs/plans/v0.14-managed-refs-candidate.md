# Future v0.14 Managed ReFS candidate plan

Status: candidate plan only. This is not a release note and the probe branch is
not a released version.

## Lineage policy

Keep public product history linear. The released v0.13 Image + native CoW
integration remains available and documented. The Managed ReFS probe begins
from v0.12 solely to isolate a storage-architecture hypothesis.

If the probe reaches PROVEN, integration starts from the then-current `main`:

1. inspect every change after v0.13;
2. port `internal/refsworkspace`, the standalone probe, and focused tests;
3. adapt the code to current service, history, metrics, and CLI contracts;
4. preserve `image-cow` behavior and benchmark documents;
5. add a separately reviewed `refs` workspace backend;
6. run legacy, image, image-cow, and refs compatibility gates; and
7. prepare a future v0.14.0 candidate only after native evidence is reviewed.

Squash or selected cherry-picks are acceptable when they preserve provenance
and yield a clean latest-main implementation. If architecture conflicts are
large, implement the final shape again on latest `main` instead of merging the
research branch wholesale.

## Gate progression

### Phase 1: pool capability

- Dynamic VHDX setup without Hyper-V cmdlets
- read-only Dev Drive capability preflight with no global policy mutation
- GPT/max partition, unused temporary drive letter, `Format-Volume -DevDrive`,
  `fsutil devdrv query`, private directory mount, and temporary-letter removal
- persistent detached lifecycle: status/probe never format and only remove deletes
- exact VHDX/volume/token ownership
- synthetic native Block Clone and allocate-on-write isolation
- clean unmount/detach/remove
- regular and sparse allocated-range Block Clone
- measured residuals with no implicit zero values
- host free-space floor before setup and worker acquire
- verified metadata-only `PoolPolicy`; no request-level policy overrides
- fresh missing-parent creation with intermediate reparse rejection
- exact residual allowlists with unknown/staging evidence and an outer process check

Exit: PROMISING is possible after native synthetic success.

### Phase 2: canonical Library baseline

- full compatibility key timings
- isolated Unity builder targeting ReFS staging directly
- COMPLETE-last atomic commit
- recursive read-only/ACL/hash protection for child directories and files
- corruption quarantine and active-use clear refusal
- per-key atomic use-versus-mutation coordination
- persisted protection evidence and hash-cost metrics

### Phase 3: workers and correctness

- 1/2/4/8 worker ladder
- junction and lease lifecycle
- legacy semantic parity
- source, baseline, and sibling isolation
- host/ReFS/Library allocation metrics
- zero cleanup residual
- atomic pool-wide reservation under concurrency
- same-process, same-object idempotent milestone-based release after injected failures

Exit: PROVEN requires all Phase 1–3 native gates.

### Phase 4: latest-main integration proposal

Only after PROVEN, draft the public CLI and migration design. A possible policy
for review is:

```text
refs      → recommended Windows experimental backend
image-cow → released v0.13 experimental/legacy backend
image     → physical correctness control
```

No default switch or deprecation is implied by this plan.

## Pre-native hardening gate

Static tests must show that callers cannot override verified pool policy,
concurrent workers cannot over-reserve, setup reserves maximum VHDX growth,
fresh paths reject reparse escapes, host free space is remeasured inside the
lock, baseline use cannot race clear/quarantine, recursive protection damage is
detected without a content change, same-object release resumes after each
milestone, sparse query pages are clipped/merged without no-progress loops,
and unknown residuals and cleanup errors remain visible.

Passing this gate means only `STATIC READY FOR DEV DRIVE VALIDATION`. Native
Windows Dev Drive setup, regular/sparse Block Clone, Unity correctness, 1/2/4/8
isolation, allocation deltas, and residual cleanup retain their measured or
`NOT MEASURED` status.

## Explicit non-goals

- changing any v0.13 tag, release, artifact, commit, or benchmark;
- public default-backend changes in the probe branch;
- HoneyBee integration;
- whole-workspace ReFS cloning;
- Git worktree or scenario orchestration;
- automatic compact or resize;
- complete forced-termination or reboot recovery;
- new-process `ResumeLeaseFromJournal`, `RecoverOrphanWorker`, or `ReconcilePool`;
- every Windows SKU; and
- cross-platform ReFS.

## Integration recommendation states

- `continue probe`: platform-independent or synthetic work remains.
- `ready to port to latest main`: all PROVEN criteria have native evidence.
- `unsupported`: ReFS format or Block Clone is unavailable with a recorded
  Windows edition, build, policy, and error.
- `abandon`: a supported environment fails correctness, ownership, isolation,
  or cleanup and the architecture no longer offers a safe path.
