§0 · 한 줄 결론

현재의 testplay는 "잘 만들어졌지만 아직 발견되지 않은 도구"다. 비교 데이터가 말하는 것은 명확하다 — "Unity 테스트 자동화" 시장만으로는 6년 현직 1위도 257★가 천장이지만, "Unity × AI 에이전트" 물결은 16개월 만에 12,198★를 만들었다. testplay의 상방은 테스트 도구가 아니라 AI 에이전트 인프라로 포지셔닝될 때 열린다. 제품의 기술적 차별성(warm bridge, honest contract)은 이미 그 포지셔닝을 뒷받침할 수준이다. 부족한 것은 유통(발견 가능성·온보딩·생태계 연결)뿐이며, 그것이 현재 5.1과 포텐셜 8.3의 격차 전부다.

§4 · 예측

12개월 시나리오 — 무엇을 하느냐가 자릿수를 정한다

기준 시점: v1.0 GA 런치로부터 12개월. 확률은 "문서 26의 전략을 실행한다"는 조건부. 스타는 멱법칙 분포이므로 점 추정이 아니라 범위로 읽어야 한다.

S0 · 전략 미실행 시의 기본값
현상 유지
5–30 ★

런치도 생태계 연결도 없이 코드만 좋은 상태. 발견되지 않은 니치 도구의 압도적 다수가 머무는 구간. 지금까지의 궤적(3.5개월, 1★)이 그대로 연장된 값.

v1.0 + 런치 실행
150–600 ★

S3 · 확률 ~10% 미만
브레이크아웃

HN 프론트페이지급 바이럴 1회 + PlayMode/네트워크 테스트로 카테고리 자체를 정의. unity-mcp의 궤적. 계획할 수는 없지만, S2까지 실행해야 복권을 살 자격이 생기는 구간.

정직한 기대값 정리: 전략을 실행하면 중앙값 기준 ~300★이 현실적인 12개월 목표선이고, 확률가중 기대값은 상방 꼬리(S2·S3) 덕분에 500–900★까지 끌려 올라간다. 전략을 실행하지 않으면 두 자릿수에서 멈춘다. 즉 이 프로젝트의 스타 수는 코드가 아니라 남은 유통 실행에 달려 있다 — 코드 쪽 숙제는 이미 대부분 끝났기 때문이다.

§5 · 레버 & 리스크

자릿수를 바꾸는 것 셋, 발목을 잡는 것 넷

자릿수를 바꾸는 레버

  • GitHub Action + JUnit (A-2·A-5) — CI-side 최대 레버. MCP가 인터랙티브 전용이라 CI 절반에 무효인 것과 정반대로, Action은 CI 네이티브라 그 절반을 커버하고 두 번째 계약을 만들지 않는다(바이너리를 실행하고 exit code+JSON을 PR 인라인 어노테이션으로 번역만). autofix 봇에게 exit code=트리거, JSON=수리 페이로드.
  • 런치 모먼트 (C-4) — 스타는 순간에 온다. GA + 글 + GIF + 등재를 한 주에 겹칠 것. 첫 48시간 댓글 대응이 가능한 시기(휴가)에 배치.
  • 5분 성공 경로 (B-1·B-2·B-3) — brew, Unity 자동탐지, examples. 유입을 스타로 전환하는 깔때기의 바닥.

리스크

  • 시간 제약 — 군복무 중 조각난 시간. 런치 타이밍을 놓치면 S1 확률이 깎인다. 보완: v1.0 범위를 좁게 유지, 확장은 v1.x로.
  • game-ci와의 경계 — Unity 라이선스·설치는 Action 범위 밖. "경쟁"이 아니라 "game-ci로 Unity 세팅 + testplay-action으로 테스트 결과 계약"이라는 보완 포지션을 문서로 못박지 못하면 혼란·중복으로 읽힌다.
  • 니치의 절대 크기 — Unity 자동화 모수 자체가 작다. 소셜 증명 포텐셜을 6/10으로 잡은 이유. 스타 그래프에 일희일비하지 말 것.
  • 검증 부채 — scenario 모드 완결(--filter 전파) 전에 런치하면 Case Study 0002류 이탈이 재현된다. 완성도 → 유통 순서는 바꿀 수 없다.

방법론: 참조군 예측(reference-class forecasting). 비교군 스타 수는 2026-07-08 GitHub REST API 실측값. 시나리오 확률은 비교군 궤적과 전략 실행 가정에 기반한 주관적 추정이며, 스타 수는 멱법칙 분포라 분산이 크다. 이 문서는 의사결정 보조용이지 보장이 아니다.

레이팅 산정: 10개 차원 × 0–10점 단순 평균. 차원 정의와 점수 근거는 각 막대에 마우스를 올리면 표시된다.
